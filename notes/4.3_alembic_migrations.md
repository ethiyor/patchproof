## Library: Alembic

**What it is:** A database migration tool built on top of SQLAlchemy. It tracks which migrations have been run and applies only the new ones.

**The problem it solves:** When your schema changes (add a column, rename a table, add an index), you need a way to update the real database without deleting everything and starting over. Alembic manages this with migration files.

---

## Concept: Migrations

A **migration** is a Python file with two functions:

```python
def upgrade() -> None:
    # SQL changes to apply when going forward
    op.create_table("users", ...)
    op.add_column("reviews", sa.Column("new_field", sa.String()))

def downgrade() -> None:
    # SQL changes to undo this migration
    op.drop_column("reviews", "new_field")
    op.drop_table("users")
```

`upgrade()` runs when you apply the migration (`alembic upgrade head`).
`downgrade()` runs when you undo it (`alembic downgrade -1`).

Every migration has a `revision` ID and a `down_revision` that points to its parent — this forms a chain:

```
None  ←  001_initial_schema  ←  002_add_indexes  ←  003_add_user_role
                                                     (current head)
```

`alembic upgrade head` runs all migrations up to the newest. `alembic downgrade -1` undoes the last one. `alembic current` shows which migration the DB is at right now.

---

## Concept: `alembic_version` table

When Alembic runs on a database for the first time, it creates a special table:

```sql
CREATE TABLE alembic_version (
    version_num VARCHAR(32) NOT NULL PRIMARY KEY
);
```

After each migration runs, it inserts the revision ID into this table:

```sql
INSERT INTO alembic_version VALUES ('001');
```

The next time you run `alembic upgrade head`, it reads `alembic_version` to know which migrations have already been applied and skips them. This is how Alembic knows the state of your database.

## Concept: Offline vs Online mode

Alembic has two modes:

**Online mode** (`alembic upgrade head`): connects to a real database and runs SQL.

**Offline mode** (`alembic upgrade --sql head`): prints the SQL to stdout without connecting to a database. Used for:
- Reviewing what will run before touching production
- Generating a `.sql` file for a DBA to review
- CI pipelines where a live DB isn't available

The `env.py` file handles both modes:

```python
if context.is_offline_mode():
    run_migrations_offline()   # prints SQL
else:
    run_migrations_online()    # runs SQL on the DB
```

## Concept: Why async `env.py` is different

The default `env.py` from `alembic init` uses synchronous SQLAlchemy. Since PatchProof uses async SQLAlchemy (`asyncpg` driver), the `env.py` needs a special pattern:

```python
async def run_async_migrations() -> None:
    connectable = async_engine_from_config(...)
    async with connectable.connect() as connection:
        await connection.run_sync(do_run_migrations)  # ← key line
    await connectable.dispose()

def run_migrations_online() -> None:
    asyncio.run(run_async_migrations())  # bridges async → sync entry point
```

**`connection.run_sync(do_run_migrations)`** — Alembic's migration code is synchronous (it uses old SQLAlchemy Core). `run_sync()` runs a synchronous function inside an async connection context. This is the bridge between the async driver and Alembic's sync internals.

**`asyncio.run()`** — Alembic's entry point is synchronous (it's a command-line tool). `asyncio.run()` creates an event loop, runs the async function to completion, and returns. This bridges the command-line tool (sync) to the async code.

## Concept: `op` — Alembic's migration operations

Inside migration functions, `op` is the Alembic operation object. It provides high-level methods for schema changes:

```python
from alembic import op
import sqlalchemy as sa

op.create_table("users", ...)          # CREATE TABLE
op.drop_table("users")                 # DROP TABLE
op.add_column("users", sa.Column(...)) # ALTER TABLE ... ADD COLUMN
op.drop_column("users", "email")       # ALTER TABLE ... DROP COLUMN
op.create_index("idx_name", "users", ["email"])  # CREATE INDEX
op.drop_index("idx_name")              # DROP INDEX
```

These are database-vendor-agnostic. Alembic translates them to the correct SQL for your database dialect (PostgreSQL, MySQL, SQLite, etc.).

## Concept: `--autogenerate` vs manual migrations

**`alembic revision --autogenerate -m "description"`**
Alembic connects to the DB, inspects the current schema, compares it to `Base.metadata` (your models), and generates a migration file containing only the *differences*. Fast and convenient, but requires a live DB and always needs human review.

**Manual migration** (what we did in milestone 4.3)
You write the `upgrade()` and `downgrade()` functions yourself. More work, but 100% explicit. For the first migration (empty DB → 7 tables), manual is actually cleaner since there's nothing to "diff" against.

In practice, most teams use `--autogenerate` for incremental changes (adding a column, renaming a table) and review the output before committing. You'll use both patterns in Phase 4.

## Migration order matters (foreign keys)

The tables in `upgrade()` are created in dependency order:
```
users              (no dependencies)
repositories       (no dependencies)
pull_requests      (depends on repositories)
reviews            (depends on repositories, pull_requests)
review_findings    (depends on reviews)
requirement_checks (depends on reviews)
changed_files      (depends on reviews)
```

And in `downgrade()`, they're dropped in **reverse** order — child tables before parent tables — because you can't drop a table that has foreign key references pointing at it.
