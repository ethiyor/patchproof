# Milestone 5.4 - Webhook-triggered background PR analysis

## What changed

Milestone 5.4 connects the GitHub webhook from milestone 5.2 and the GitHub App authentication from milestone 5.3 to the existing PatchProof review pipeline.

Before this milestone, the backend could verify that a webhook really came from GitHub, but it did not use that webhook to run a review. Now, when GitHub sends a signed `pull_request` webhook, PatchProof accepts the event immediately and schedules the actual PR analysis as a FastAPI background task.

## Request flow

1. GitHub sends a webhook to `POST /github/webhook`.
2. The backend reads the raw request body.
3. The backend verifies `X-Hub-Signature-256` with `GITHUB_WEBHOOK_SECRET`.
4. Non-`pull_request` events are ignored with a `200` response.
5. `pull_request` events are parsed for the fields PatchProof needs:
   - `installation.id`
   - `repository.full_name`
   - `pull_request.number`
   - `pull_request.body`
6. The endpoint schedules `process_pull_request_webhook(...)` with FastAPI `BackgroundTasks`.
7. The endpoint returns `202 Accepted` immediately.

The important design choice is that GitHub does not wait for the full LLM review to finish. The webhook response is fast, and the slower review work happens after the response has already been accepted.

## Background task flow

The new background processor lives in `backend/services/github_webhook_processor.py`.

It performs the actual PR review work:

1. Uses `GitHubAppClient` to get an installation access token for the `installation.id`.
2. Uses `GitHubClient` with that installation token.
3. Fetches fresh PR metadata from GitHub.
4. Fetches the PR diff from GitHub.
5. Chooses the task text in this order:
   - webhook PR body
   - fetched PR body
   - linked issue body, if GitHub metadata found one
6. Reuses the existing review persistence helpers from `backend/api/reviews.py`.
7. Saves or updates the repository record.
8. Saves or updates the pull request record.
9. Runs the PatchProof analysis pipeline.
10. Saves the review, changed files, findings, risk data, and structured report data in the database.

Milestone 5.4 stops after saving the review. Posting the result back to the GitHub PR is intentionally left for milestone 5.5.

## Files changed

- `backend/api/github_webhook.py`
  - Added FastAPI `BackgroundTasks`.
  - Parses signed `pull_request` webhook payloads.
  - Queues background PR analysis.
  - Returns `202 Accepted` immediately for valid PR webhook events.

- `backend/services/github_webhook_processor.py`
  - Added `PullRequestWebhookEvent`, a small typed object containing only the webhook fields PatchProof needs.
  - Added `parse_pull_request_webhook(...)` for payload validation and extraction.
  - Added `process_pull_request_webhook(...)` for token fetching, PR diff fetching, analysis, and database persistence.
  - Added fallback task text selection from PR body to linked issue body.

- `tests/unit/test_webhook_verifier.py`
  - Updated endpoint tests so valid PR webhooks assert that a background analysis task is scheduled.
  - Kept coverage for invalid signatures, missing signatures, ignored events, invalid JSON, missing payload fields, and missing webhook secret.

- `tests/unit/test_github_webhook_processor.py`
  - Added tests for webhook parsing.
  - Added tests that the processor fetches an installation token, fetches PR metadata/diff, and saves a review.
  - Added coverage for linked issue fallback text.
  - Added coverage for empty diffs being skipped.

## What this means in plain language

PatchProof can now react to a real GitHub pull request event.

When someone opens or updates a PR in a repository where the GitHub App is installed, GitHub can call the backend webhook. The backend verifies the request, gets GitHub access through the app installation, downloads the PR diff, runs the existing PatchProof review pipeline, and stores the result in PostgreSQL.

This is the bridge from "manual backend review endpoint" to "automatic GitHub-triggered review."
