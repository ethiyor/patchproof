# Milestone 1.4 — Rule-Based Risk Scorer

**Phase:** 1 | **Date:** 2026-07-04

## What was built

A fully deterministic risk scorer. Takes a `ParsedDiff`, applies a table of rules, and returns a `RiskScore` — a numeric score (0–∞), a level label (low/medium/high/critical), and a list of human-readable reasons. No randomness, no LLM — the same diff always produces the same score.

## Library: Pydantic (continued from 1.3)

The `RiskScore` model is also a Pydantic `BaseModel`. Two new concepts appear here:

**`Literal` for the level field:**

```python
from typing import Literal

RiskLevel = Literal["low", "medium", "high", "critical"]

class RiskScore(BaseModel):
    score: int
    level: RiskLevel
    reasons: list[str]
```

`RiskLevel` is a **type alias** — we give the `Literal[...]` union a name so we can reuse it. Using `Literal` means Pydantic will reject any string that isn't one of those four values. This is the Pydantic equivalent of an enum, but lighter weight.

**`__str__` on a Pydantic model:** We added a custom `__str__` method so `print(risk_score)` gives `"5 (Medium)"` instead of the full Pydantic repr. Pydantic models are regular Python classes — you can add methods to them freely.

## Concept: Deterministic vs Non-Deterministic Systems

**Deterministic:** Given the same input, always produces the same output. The rule-based scorer is deterministic — `compute_risk(diff)` will return the exact same `RiskScore` every time for the same `diff`.

**Non-deterministic:** Given the same input, may produce different outputs. LLMs are non-deterministic — even at temperature 0.0, tiny floating-point differences can cause different completions. This is why we build the rule-based score first and only let the LLM make a small bounded adjustment (±2) in Phase 2. The human-readable reasons always point to specific rules that fired, not to LLM opinions.

This distinction matters enormously in testing: you can write `assert result.score == 5` for the rule-based scorer. You cannot do that for an LLM — you can only assert that the output has the right shape.

## Concept: Set Operations for Rule Matching

Instead of checking each flag one by one with `if/elif`, the scorer collects all risk flags from all files into a single Python `set`, then uses **set intersection** to check if any relevant flags are present:

```python
# Collect all flags from all files
all_flags: set[str] = set()
for f in diff.files:
    all_flags.update(f.risk_flags)

# Check: does this diff touch anything auth-related?
AUTH_FLAGS = {"auth", "login", "permissions", "security"}
if all_flags & AUTH_FLAGS:          # & = intersection
    score += 3
```

**`set.update()`** — adds all items from an iterable to the set. Duplicates are discarded automatically (sets have no duplicates by definition).

**`set & set` (intersection)** — returns a new set containing only the items present in BOTH sets. If the result is non-empty, Python treats it as `True` in a boolean context.

```python
{"auth", "config"} & {"auth", "login", "permissions"}  # → {"auth"}  → truthy
{"config"}         & {"auth", "login", "permissions"}  # → set()    → falsy
```

This is much cleaner than:
```python
# Don't do this:
if "auth" in all_flags or "login" in all_flags or "permissions" in all_flags or "security" in all_flags:
```

Sets are a fundamental data structure. They are backed by a hash table (like dict keys), so membership checks (`in`) are O(1) — constant time regardless of how many flags exist.

## Concept: Scoring as a Decision Table

The scoring rules are a **decision table** — a list of conditions, each with an associated action (change the score, add a reason). Decision tables are a classic software pattern for encoding business rules:

```
Condition                         | Action
---------------------------------|------------------
file path contains "auth"         | score += 3
file path contains "payments"     | score += 3
migration file present            | score += 2
no test files changed             | score += 2
total lines > 500                 | score += 1
tests changed                     | score -= 2
```

In code, each rule is an `if` block — one condition, one or more score/reason mutations. This pattern is easy to extend: adding a new rule is just adding a new `if` block. The rules are independent of each other (no `elif`) so multiple rules can fire for the same diff.

---

## Concept: Score Flooring

Scores can go negative if the only rules that fire are deductions (like tests present → -2). A negative risk score is meaningless and confusing. The floor:

```python
score = max(0, score)
```

`max(a, b)` returns the larger of two values. `max(0, -2)` returns 0. This single line prevents the score from going below zero regardless of how many deductions apply.

Importantly, the **reasons list is populated before the floor is applied** — so the user still sees `"Tests added or updated (-2)"` in the reasons even when the floor prevents it from affecting the final number. The reasons explain the scoring logic, not just the final score.

## Concept: Level Thresholds — Ordered Range Check

Mapping a score to a level label is an ordered range check:

```python
_THRESHOLDS: list[tuple[int, RiskLevel]] = [
    (9, "critical"),
    (6, "high"),
    (3, "medium"),
    (0, "low"),
]

def _level(score: int) -> RiskLevel:
    for threshold, level in _THRESHOLDS:
        if score >= threshold:
            return level
    return "low"
```

This walks the list from highest to lowest and returns the first match. A score of 7 hits `6 → high` first and returns immediately. A score of 2 misses 9, 6, and 3, then hits `0 → low`.

Why a list of tuples instead of `if/elif`? Because the thresholds are **data** — they could come from a config file or database. Separating the data from the logic (`if score >= threshold`) makes it easy to change the thresholds without rewriting the function.

## Concept: Synthetic Test Objects

The test file uses a `_make_diff()` helper that builds a `ParsedDiff` from scratch without needing a fixture file:

```python
def _make_diff(
    flags: list[str] | None = None,
    has_test_changes: bool = False,
    total_files: int = 2,
    ...
) -> ParsedDiff:
    primary = ParsedFile(path="backend/main.py", risk_flags=flags or [])
    return ParsedDiff(
        files=[primary],
        has_test_changes=has_test_changes,
        ...
    )
```

This lets you test one rule in isolation without needing a real diff file:

```python
# Test the auth rule in isolation:
without = compute_risk(_make_diff(flags=[])).score        # baseline
with_auth = compute_risk(_make_diff(flags=["auth"])).score  # + auth
assert with_auth == without + 3
```

This is **unit testing** — testing a single unit of behavior with all other variables controlled. Contrast with the `TestFixtureIntegration` class which uses real `.diff` files — that is closer to **integration testing** (testing that multiple real components work together).

**One subtle bug found and fixed:** The test `test_no_tests_adds_2` originally checked that `without_tests == with_tests + 4`. But when `with_tests` is floored to 0 (raw score would be -2), the visible difference is only 2, not 4. The fix was to use `flags=["auth"]` as the base score so the floor never interferes:

```python
# with auth(+3) as base:
# auth + no-tests:  3 + 2 = 5
# auth + tests:     3 - 2 = 1
# difference:       4 ✓  (floor never fires because 1 > 0)
```

This is a real lesson: **floor/ceiling effects change observable differences**. Always test with a base score above the floor when testing deduction rules.
