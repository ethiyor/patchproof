# Milestone 5.2 - Webhook Endpoint with Signature Verification

**Phase:** 5 | **Date:** 2026-07-07

## What this milestone does

PatchProof now exposes a secure GitHub webhook endpoint:

```text
POST /github/webhook
```

The endpoint verifies GitHub's `X-Hub-Signature-256` HMAC signature against the
raw request body before accepting any event. Invalid or missing signatures are
rejected immediately with `403`.

This milestone does not run PR analysis yet. Background analysis starts in
milestone 5.4. For now, valid `pull_request` events are accepted with `202`, and
valid non-`pull_request` events are ignored with `200`.

## Files changed

| File | Purpose |
|---|---|
| `backend/services/webhook_verifier.py` | Builds and verifies GitHub SHA-256 webhook signatures using HMAC and constant-time comparison |
| `backend/api/github_webhook.py` | Adds `POST /github/webhook` and enforces signature verification before event handling |
| `backend/main.py` | Registers the GitHub webhook router with the FastAPI app |
| `tests/unit/test_webhook_verifier.py` | Covers valid signatures, invalid signatures, missing signatures, ignored events, and endpoint responses |

## Critical step 1 - Read the raw request body

The endpoint uses:

```python
payload = await request.body()
```

This is important because GitHub signs the exact raw bytes it sends. If the app
parsed JSON first and then re-serialized it, whitespace or ordering could change
and the HMAC would not match.

## Critical step 2 - Verify `X-Hub-Signature-256`

The verifier computes:

```python
"sha256=" + hmac.new(secret.encode("utf-8"), payload, hashlib.sha256).hexdigest()
```

Then it compares the expected value with GitHub's header using:

```python
hmac.compare_digest(expected, signature_header)
```

`compare_digest` is used because it is a constant-time comparison helper, which
avoids leaking useful timing information about the secret or expected digest.

## Critical step 3 - Reject bad requests before processing

If the signature is missing, malformed, signed with another algorithm, signed
with the wrong secret, or the backend has no `GITHUB_WEBHOOK_SECRET` configured,
the endpoint does not process the event.

Responses:

| Situation | Response |
|---|---|
| Missing or invalid signature | `403` |
| Missing backend webhook secret | `500` |

The secret value is never logged.

## Critical step 4 - Ignore unrelated GitHub events

If the request is validly signed but `X-GitHub-Event` is not `pull_request`, the
endpoint returns:

```json
{"status": "ignored", "event": "ping"}
```

with HTTP `200`.

This lets GitHub's initial `ping` delivery succeed without triggering review
work.

## Critical step 5 - Accept pull request events

If the request is validly signed and the event is `pull_request`, the endpoint
returns:

```json
{"status": "accepted"}
```

with HTTP `202 Accepted`.

Future milestones will attach background PR analysis to this accepted path.

## Manual testing with ngrok

With your current tunnel, the GitHub App webhook URL should be:

```text
https://charcoal-deflator-evaluator.ngrok-free.dev/github/webhook
```

After saving that webhook URL and secret in GitHub, GitHub may send a `ping`
event. If the secret matches your local `.env`, PatchProof should return `200`
for that ping event.
