# Milestone 4.5 - POST /reviews/github-pr Endpoint

**Phase:** 4 | **Date:** 2026-07-06

## What was built

The backend can now accept a GitHub pull request URL, fetch the PR metadata and diff, analyze the diff with the same PatchProof engine, save the review to the database session, and return a `ReviewResponse`.

It also reuses existing `Repository` and `PullRequest` rows when the same PR is reviewed again, avoiding unique-constraint failures in PostgreSQL.

## Files changed

| File | Purpose |
|---|---|
| `backend/schemas/review_schemas.py` | Added `GithubPRReviewRequest` with `pr_url` and optional `task` |
| `backend/api/reviews.py` | Added `POST /reviews/github-pr` and extracted shared review analysis/persistence helper |
| `tests/unit/test_reviews_api.py` | Added mocked endpoint tests for success, task fallback, persistence, and error paths |

## Request flow

```text
POST /reviews/github-pr
  -> parse PR URL
  -> create GitHubClient from backend settings token
  -> fetch PR metadata
  -> fetch raw PR diff
  -> choose task text
  -> parse diff
  -> compute deterministic risk score
  -> optionally run LLM pipeline if OPENAI_API_KEY is configured
  -> generate Markdown report
  -> get or create Repository and PullRequest rows
  -> save Review and ChangedFile rows
  -> return ReviewResponse
```

## Task fallback order

PatchProof needs a task/specification to verify the code against. The backend now chooses it in this order:

1. `task` sent in the request body
2. PR body/description
3. linked issue body, if the PR metadata includes one

If none of those exist, the endpoint returns `400` with a clear message.

## Important concept: backend endpoint vs CLI command

The Phase 3 CLI command already knew how to review a PR. Milestone 4.5 moves that capability behind HTTP:

```text
CLI-only flow:
developer machine -> patchproof review-pr -> GitHub + local analysis

Backend flow:
client/dashboard/GitHub App -> FastAPI -> GitHub + shared analysis -> database
```

This matters because future clients do not need to reimplement review logic. The VS Code extension, dashboard, or GitHub App can all call the same backend endpoint.

## Important concept: shared helper

`/reviews/local` and `/reviews/github-pr` both end with the same core operation: analyze a raw diff against task text and save the result. That shared operation now lives in `_analyze_and_save_review(...)`.

That keeps the two endpoints focused:

- `/reviews/local` receives the diff directly from the caller.
- `/reviews/github-pr` first fetches the diff from GitHub.
- Both use the same parser, risk scorer, report generator, optional LLM pipeline, and database write logic.

## Error handling

| Situation | Response |
|---|---|
| Invalid PR URL | `400` |
| Missing backend `GITHUB_TOKEN` | `400` |
| GitHub API fetch error | `502` |
| PR has no file changes | `400` |
| No task text found | `400` |

## Tests added

The tests mock `GitHubClient`, so they do not call real GitHub and do not require a real token.

Covered behavior:

- successful PR review returns `200`
- GitHub metadata and diff are fetched using parsed owner/repo/PR number
- report includes repository and PR context
- explicit request task wins over PR body
- PR body is used when request task is missing
- linked issue body is used when PR body is empty
- repository, pull request, and review objects are saved
- existing repository and pull request rows are reused
- invalid URL, missing token, GitHub errors, and empty diffs return clear errors
