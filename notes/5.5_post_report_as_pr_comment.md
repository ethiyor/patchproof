# Milestone 5.5 - Post Report as PR Comment

## What changed

Milestone 5.5 takes the saved PatchProof review from milestone 5.4 and posts it back to GitHub as a pull request conversation comment.

Before this milestone, the GitHub webhook could trigger analysis and save the review in PostgreSQL, but the result stayed inside PatchProof. Now PatchProof can publish the saved Markdown report to the PR so the developer sees the review directly in GitHub.

## Request flow

A manual endpoint was added:

```text
POST /reviews/{review_id}/comment
```

That endpoint:

1. Loads the saved review by `review_id`.
2. Confirms the review is linked to a repository and pull request.
3. Reads the repository owner, repository name, pull request number, and GitHub App installation id.
4. Gets a short-lived installation token using `GitHubAppClient`.
5. Formats the saved `report_markdown` for GitHub.
6. Calls GitHub's issue comment API for the PR.
7. Returns the `comment_url` from GitHub.

GitHub pull request conversation comments use the Issues comments endpoint:

```text
POST /repos/{owner}/{repo}/issues/{pr_number}/comments
```

This is normal GitHub API design: every pull request is also an issue conversation.

## Automatic webhook flow

The webhook background processor now also triggers commenting after the review is saved:

1. GitHub sends a signed `pull_request` webhook.
2. PatchProof verifies the webhook.
3. PatchProof fetches the PR diff.
4. PatchProof runs analysis.
5. PatchProof saves the review to the database.
6. PatchProof posts the saved Markdown report to the PR.

The repository record now stores the GitHub App `installation_id` from the webhook, because the comment endpoint needs that id later to request an installation access token.

## Failure behavior

Comment posting is intentionally one attempt.

If GitHub rejects the comment request, PatchProof logs the error and does not retry forever. This avoids duplicate comments and avoids a background loop that keeps hitting GitHub.

The manual endpoint returns:

- `200` with `comment_url` when the comment is posted.
- `404` when the review id does not exist.
- `400` when the review cannot be commented on, for example when it is not linked to a GitHub PR or the repository is missing an installation id.

## What this means in plain language

PatchProof now closes the loop on GitHub PR review automation.

A PR event can trigger PatchProof, PatchProof can analyze the PR, save the result, and publish the Markdown report directly as a GitHub PR comment. This turns PatchProof from a backend-only reviewer into a GitHub App workflow that developers can see inside their normal pull request page.
