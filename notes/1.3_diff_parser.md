## Library: Pydantic

**What it is:** A Python library for data validation using type annotations. You define a class that inherits from `BaseModel`, annotate its fields with types, and Pydantic automatically validates that any data you put into it matches those types.

**Why we use it:** Every piece of data that flows through PatchProof — diff files, LLM responses, risk scores, API request/response bodies — passes through a Pydantic model. This means if something is wrong (wrong type, missing field, unexpected value), you get a clear error immediately rather than a confusing `AttributeError` or `KeyError` deep inside the pipeline.

**How it works:**

```python
from pydantic import BaseModel

class Hunk(BaseModel):
    header: str
    lines: list[str]
    additions: int
    deletions: int
```

When you create a `Hunk`, Pydantic validates every field:

```python
Hunk(header="@@ -1,3 +1,4 @@", lines=["+new line"], additions=1, deletions=0)
# ✓ works

Hunk(header="@@ -1,3 +1,4 @@", lines="not a list", additions=1, deletions=0)
# ✗ ValidationError: lines must be a list
```

**`BaseModel` vs `@dataclass`:** Python's built-in `@dataclass` also auto-generates `__init__`, but it does NOT validate types — you can put a string in an `int` field and Python won't complain. Pydantic validates at construction time. This matters a lot when you're parsing LLM JSON responses (Phase 2), because the LLM can return anything.

**`Literal` type for enums:** The `status` field on `ParsedFile` uses `Literal["added", "modified", "deleted", "renamed"]`. This tells Pydantic that the field can only ever hold one of those four exact strings. Any other value raises a `ValidationError`.

```python
from typing import Literal

class ParsedFile(BaseModel):
    status: Literal["added", "modified", "deleted", "renamed"] = "modified"
```

**Default values:** Fields with `= []` or `= None` are optional — they don't need to be passed when creating the model.

## Concept: The Unified Diff Format

A unified diff is the standard text format for representing code changes. It is the output of `git diff` and is what GitHub shows you in a pull request. Understanding this format is essential for anyone working with code review tooling.

### Full annotated example

```
diff --git a/backend/auth/jwt_handler.py b/backend/auth/jwt_handler.py
│                                                                     │
│  ← "diff --git a/OLD_PATH b/NEW_PATH"                               │
│     This line starts a new file block. Everything until the next    │
│     "diff --git" belongs to this file.                              │

index e5f6a7b..f6a7b8c 100644
│  ← Git object hashes + file permissions. We ignore this line.      │

--- a/backend/auth/jwt_handler.py
+++ b/backend/auth/jwt_handler.py
│  ← These lines repeat the file paths. "---" = old version,        │
│     "+++" = new version. We SKIP these — they look like code        │
│     deletions/additions but they are not.                           │

@@ -12,9 +12,9 @@ import os
│  ← Hunk header. Format: @@ -OLD_START,OLD_COUNT +NEW_START,NEW_COUNT @@ CONTEXT
│     -12,9 means: in the OLD file, this block starts at line 12     │
│     and spans 9 lines.                                              │
│     +12,9 means: in the NEW file, this block starts at line 12     │
│     and spans 9 lines.                                              │
│     "import os" is optional context shown after the @@.            │

 SECRET_KEY = os.getenv("SECRET_KEY", "changeme")
│  ← Context line. Starts with a SPACE. This line is UNCHANGED.      │
│     It's shown so you know where in the file you are.              │

-ACCESS_TOKEN_EXPIRE_MINUTES = 30
│  ← Deletion. Starts with "-". This line was REMOVED.              │

+ACCESS_TOKEN_EXPIRE_MINUTES = 60
│  ← Addition. Starts with "+". This line was ADDED.                │
```

### Key rules to remember

| Line starts with | Meaning |
|---|---|
| `diff --git a/X b/Y` | Start of a new file block |
| `new file mode` | File was created (status = added) |
| `deleted file mode` | File was deleted (status = deleted) |
| `rename from X` / `rename to Y` | File was moved (status = renamed) |
| `--- ` | Old file path — skip, not a deletion |
| `+++ ` | New file path — skip, not an addition |
| `@@ ... @@` | Hunk header — new block of changes starts |
| `+` (not `+++`) | Added line — count as addition |
| `-` (not `---`) | Removed line — count as deletion |
| ` ` (space) | Context line — unchanged, just for reference |

### What a hunk is

A single file can have multiple hunks. Each hunk represents one contiguous block of changes. If you changed line 5 and also line 200, git produces two separate hunks — one around line 5 and one around line 200. This is why `ParsedFile.hunks` is a list.

## Concept: Parsing Strategy — Dicts First, Models Last

During parsing we don't build Pydantic models immediately. We accumulate data in plain Python dicts, then build models at the very end:

```python
# During parsing: plain dicts
current = {"path": "...", "status": "modified", "hunks": [], "additions": 0}
current["additions"] += 1  # simple dict mutation

# At the end: build Pydantic model from the completed dict
ParsedFile(**block)  # validation happens here, once
```

**Why not build Pydantic models directly and mutate them?** You can mutate Pydantic v2 model instances (they are mutable by default), but it requires special handling to bypass validation on each assignment. More importantly, partial models — objects where some fields haven't been set yet — are conceptually wrong. A `ParsedFile` with `additions=0` while you're still mid-parse isn't a valid intermediate state; it's just an incomplete dict. Using dicts makes the intermediate state explicit and keeps the final model construction clean and validated.

## Concept: State Machine Parsing

The parser is a simple **state machine** — it maintains a "current state" and transitions between states as it reads each line.

```
STATE: no_file
  → sees "diff --git"  → STATE: in_file

STATE: in_file
  → sees "new file mode"  → updates status flag
  → sees "@@ ..."        → STATE: in_hunk
  → sees "diff --git"    → flush file, STATE: in_file (new file)

STATE: in_hunk
  → sees "+" line        → count addition
  → sees "-" line        → count deletion
  → sees " " line        → store context
  → sees "@@ ..."        → flush hunk, STATE: in_hunk (new hunk)
  → sees "diff --git"    → flush hunk + file, STATE: in_file (new file)
```

State machines are a fundamental pattern in parsing, compilers, networking, and UI (React state management is conceptually the same idea — the UI is a function of its current state).

## Concept: Test Fixtures vs Unit Tests

**Test fixtures** (the `.diff` files in `tests/fixtures/`) are static input files that represent realistic real-world scenarios. They make tests deterministic — every run uses the exact same input. They also document what the system is designed to handle.

**Unit tests** verify one specific behavior in isolation. In the test file, each test class corresponds to one fixture or one concept:

- `TestSimpleAdd` — one new file, no risk, no tests
- `TestMigrationChange` — risky SQL migration + Python model
- `TestAuthChange` — auth module modification
- `TestEdgeCases` — empty diff, whitespace only, test file detection

**Why test classes instead of top-level functions?** `setup_method` (called before each test in a class) parses the diff once and stores the result as `self.result`. All tests in the class reuse the same parsed result. This is faster and avoids repeating the parse call in every test function.
