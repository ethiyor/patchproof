# Milestone 8.4 - Deployment Status

## Goal

Expose the backend publicly and connect it to a persistent remote database.

## What was built during deployment work

The deployment path chosen for learning was AWS instead of the Render/Fly options in the original Phase 8 doc.

The current architecture is:

```text
GitHub webhook -> AWS Application Load Balancer -> ECS Fargate service -> FastAPI container -> Amazon RDS PostgreSQL
```

## AWS pieces used

- ECR stores the PatchProof backend Docker image.
- ECS Fargate runs the container without managing EC2 instances directly.
- An ECS task definition describes the image, CPU/memory, port, and environment variables.
- An ECS service keeps the desired number of backend tasks running.
- ALB provides a stable public HTTP endpoint and routes traffic to the ECS task target group.
- RDS PostgreSQL stores repositories, pull requests, reviews, findings, requirement checks, changed files, users, and the Alembic version.
- Security groups control which traffic can reach the ALB, ECS task, and database.

## Verified behavio

- RDS migrations ran with `alembic upgrade head`.
- Tables were visible through `psql` using `\dt`.
- The backend health endpoint worked when reachable through the configured public route.
- GitHub webhook deliveries reached the deployed backend once the GitHub App webhook URL pointed at the active backend URL.

## Remaining production hardening

- Move secrets from ECS task-definition plaintext values into AWS Secrets Manager.
- Attach only the minimum required IAM permissions to the ECS execution role.
- Enable HTTPS on the ALB with ACM.
- Restrict RDS inbound access to the ECS service security group and temporary admin IPs only.
- Add CloudWatch alarms, log retention, and a documented deploy command.
